# Billing Engine (Phase 12)

The Billing Engine represents the unified hybrid billing infrastructure enabling both upfront top-ups and standard postpaid corporate invoicing.

## 1. Prepaid vs Postpaid Logic

The engine explicitly decouples the execution layer from the billing mode.
- **Prepaid Mode (`ModePrepaid`)**: Consumers top-up their balance via Stripe. When a job is routed, the engine dynamically calculates the estimated cost (`EstimatedCostUSD`). If `BalanceUSD` is less than the estimate, the job is rejected. When the result returns, `DeductBalance` subtracts the final exact `amountUSD`.
- **Postpaid Mode (`ModePostpaid`)**: Consumers execute freely (up to an eventual `CreditLimit`). Their usage is aggressively aggregated into memory via `AddInvoiceLine` and settled dynamically at the end of the month.

## 2. Customer Models

- `CustomerAccount`: The root struct tracking the `CustomerID`, their active `BillingMode`, and their floating `BalanceUSD`.
- `CustomerUsage`: Represents a granular transaction line for postpaid users. Tracks the `TaskID`, the total `WorkUnits` consumed, and the precise `AmountUSD` charged.
- `CustomerAggregate`: The consolidated structure pushed outward to the CRM. Contains a summary of `TotalWU`, `TotalUSD`, and the remaining `BalanceUSD`.

## 3. Pricing Matrix Application

The Billing Engine computes final costs by referencing the `PricingMatrix`.
When a task returns a `WorkUnits` (WU) value, the router checks the assigned operator's `TierID` to fetch the specific `PricePerWU`. 
The formula `AmountUSD = WU * PricePerWU` is evaluated before any deduction or invoice line is applied, ensuring complete price accuracy relative to the current market rate.

## 4. BillingEngine Behavior

The `BillingEngine` is heavily guarded by `sync.RWMutex` locks, making it thread-safe for concurrent task routing.
- If a customer does not exist in the ledger when queried, `EnsureAccount` creates an automatic default (usually `ModePrepaid` with `$0.00` balance).
- Reads (like `CanRunJob` or `GetAggregate`) utilize `RLock()` to prevent stalling the execution queue.
- Writes (like `DeductBalance`) utilize strict `Lock()` logic to ensure transactional safety during concurrent deductions.

## 5. Mesh Billing Integration

The integration occurs strictly within `mesh/router.go` during `handleTaskResult`:
1. The Customer ID attached to the task is retrieved from the `taskCustomers` buffer.
2. The `WU` generated by the node is converted to `AmountUSD`.
3. The engine routes the charge based on the CRM-synced `BillingMode`.

## 6. CRM Billing Sync (10-Minute Cycle)

To prevent the local mesh from dropping out of sync with the global platform, the CRM synchronization engine actively polls the billing data.
- The `SyncEngine` reads via a provided `FetchBilling` callback pointing to the `BillingEngine`.
- It processes this strictly on a 10-minute cadence.

## 7. BillingQueue

The CRM Sync module utilizes an internal `billingQueue` channel (`chan billing.CustomerAggregate`).
When the 10-minute loop triggers:
- Aggregates are fetched from the engine and buffered into the queue.
- A consumer drains the queue, executing HTTP POSTs (`PushCustomerBilling`) to the CRM.
- If the CRM API returns a 500 error or times out, the aggregate is re-enqueued to prevent billing loss.

## 8. Debug Endpoints

The billing state can be interrogated natively via:
- `GET /debug/billing/modes`: Dumps the current billing mode mapped by `CustomerID`.
- `GET /debug/billing/balances`: Returns the real-time USD balance of all prepaid customers.
- `GET /debug/billing/invoices`: Outputs the currently aggregated `TotalWU` and `TotalUSD` for postpaid corporate accounts.
