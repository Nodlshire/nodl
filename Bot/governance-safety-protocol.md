# Governance & Safety Protocol

To maintain extreme stability and architectural integrity as the Wnode codebase evolves, strict AI and developer governance rules are permanently enforced. These rules ensure that rapid iteration does not compromise core security or platform availability.

## 1. Scope Lock (File Declaration)

Before any code modification begins, the acting AI agent or developer MUST explicitly declare the target files to be modified in an Implementation Plan. 
- Modifying files outside the declared scope is strictly forbidden.
- If an architectural change requires modifying an unexpected file, development must halt until a revised Implementation Plan is drafted and formally approved by the User.

## 2. Ask-Before-Acting Rule

If a requirement is ambiguous, unstated, or theoretically conflicts with existing logic, the agent MUST stop and ask the user for clarification.
- "Making reasonable assumptions" regarding core infrastructure (e.g., billing ledgers, reputation scoring limits, or webhook payloads) is not permitted.
- Precision takes absolute precedence over speed.

## 3. No New UI Surfaces Rule

Unless explicitly requested by the User in a targeted front-end phase, backend modifications must NOT necessitate the creation of new UI surfaces.
- Data generated by the backend (such as new debug maps or economic profiles) must be piped into existing CRM dashboards or left as headless API endpoints until the User directs a specific UI phase.

## 4. Regression Scan Requirement

Before submitting a phase as "complete," the developer/agent must verify that the new functionality has not broken the build cycle. 
- Structural changes to Go structs require ensuring that upstream consuming code (like `mesh/server.go`) still compiles successfully.

## 5. Approval Gate Requirement

Execution of modifying commands or code-writing tools is strictly prohibited during the "Planning Phase".
- The agent must output an `Implementation Plan` artifact with `RequestFeedback` enabled.
- The agent must achieve explicit human approval to proceed before executing write operations to the disk.

## 6. One-Subsystem-Per-Phase Rule

To isolate bugs and ensure comprehensive documentation, development proceeds strictly in targeted phases (e.g., Phase 11: Reputation, Phase 12: Billing, Phase 13: Payouts).
- Code changes must not "bleed" into unrelated subsystems. If a refactor is required in an adjacent module to accomplish the current phase's goal, that refactor must be isolated, declared, and approved.
