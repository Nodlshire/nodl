# Mesh Operator Guidelines


> ### Contextual Architecture Narrative

> - **WHAT**: Core architectural specification for **Mesh Operator Guidelines** within the Wnode Sovereign Mesh network.

> - **WHY**: Guarantees zero-custody execution, deterministic state verification, and anti-Sybil physical radio anchoring.

> - **HOW**: Executed via SECCOMP-isolated Native Go (`linux-amd64`) modules, validated with mTLS telemetry signatures and HMAC routing epochs.



Operating a node in the Wnode Sovereign Mesh is lightweight but requires strict adherence to security configurations.

## Requirements
- **Stable RPC endpoint**: Your node must connect to a local or high-throughput RPC provider.
- **Strict Determinism**: Your configuration (`WnodeClientConfig.strictDeterminism`) MUST be set to true. The network gossip protocol aggressively prunes nodes that advertise non-deterministic execution capabilities.
- **Port Visibility**: Minimal P2P ports must be exposed to handle the UDP/TCP mesh gossip (stubbed in current phases).

## Observability
Using the `wnode` CLI or Operator Dashboard UI bindings, operators can observe:
- **Active Peers**: Who you are connected to.
- **Healthy Peers**: Peers that have successfully passed the `MeshDiscovery` determinism handshake.
- **Workflow Traces**: Steps assigned to your node via `WorkflowStepAssignment`.
- **Proof Generation**: The localized `ProofOfCompute` generated by your node prior to aggregation.

## Security Operations
Starting with Phase 1.6, the Mesh strictly enforces authentication and Byzantine fault detection:
- **Node Authentication**: You must provide a valid `authToken` upon startup. This token acts as a signed capability descriptor proving your authorization to participate in the mesh.
- **Quarantine Monitoring**: Watch your `SecuritySnapshot` metrics. If a peer violates integrity (e.g. invalid MAC proofs, mismatched payload hashes), they are flagged as suspicious and eventually **quarantined**.
- **Incident Logs**: The `MeshByzantineMonitor` exposes `getIncidentLog(nodeId)`. Operators should regularly dump this log to identify malicious peers attempting to inject invalid workflows or tampered proofs. Quarantined nodes are ignored silently by the secure transport layer to prevent network flooding.

## Persistence & Recovery
Starting with Phase 1.8, the Mesh implements deterministic crash recovery:
- **State Snapshots**: The node periodically dumps its state to the local filesystem (`FileSystemPersistenceAdapter`). These snapshots are pure JSON and hash-verified upon reload.
- **Event Journal**: All mutations are appended to an event log. If the node crashes, it reloads the latest snapshot and replays the journal to instantly and safely reconstruct its state without trusting external peers.
- **Workflow Resumption**: Any workflows interrupted during a crash will automatically resume step dispatch upon successful journal replay.
